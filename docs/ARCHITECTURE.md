# TinyH3 Video — архитектура движка

Цель: генерировать видео со звуком моделью **MiniMax H3** на **RTX 3070 8 ГБ + 16 ГБ ОЗУ**,
быстрее и экономнее, чем FreeVideo, и без загрузки модели целиком ни в видеопамять, ни в ОЗУ.

Документ фиксирует расчёты и решения. Числа ниже посчитаны из реальных конфигов
`multimodalart/MiniMax-H3-Pruned` и `Lakonik/pi-H3` (они же зашиты в `tinyh3/config.py`).

---

## 1. Что мы запускаем

| Компонент | Источник | Размер (bf16) | Как используем |
|---|---|---|---|
| DiT, 50 блоков, hidden 5376, 56×128 голов, FFN 14336 | `MiniMax-H3-Pruned/transformer` | 38.5 ГБ (19.27B параметров) | Квантуем и стримим блоки |
| Адаптер **pi-Flow 4/2 шага + DWD** | `Lakonik/pi-H3/pi_h3_{4,2}step_dwd_adapter` | 3.8 ГБ | LoRA **вливаем в веса на этапе конвертации** |
| Голова DWD (8 слоёв Sol, dim 2048) | в адаптере DWD | ~1.2 ГБ | Декодирует пиксели **без VAE-декодера** |
| Текстовый энкодер Qwen3-VL-32B, нужны 50 слоёв из 51 | `MiniMax-H3-Pruned/text_encoder` | 48.8 ГБ (24.4B) | Квантуем в int8 и стримим по слоям |
| Аудио-VAE (декодер) | `MiniMax-H3/audio_vae` | 0.6 ГБ | Как есть |

Ключевые решения:

1. **pi-Flow вместо 8 шагов DMD.** У FreeVideo 8 шагов (плюс двухпроходная схема), у нас 4 шага (Balanced)
   или 2 (Turbo). Каждый шаг — это полный проход всех 50 блоков, то есть ещё и полная прокачка весов.
   В 2–4 раза меньше шагов — в 2–4 раза меньше и вычислений, и трафика.
2. **DWD вместо VAE-декодера.** У FreeVideo VAE-декодер — 36 блоков по 268.6 МБ (~9.7 ГБ), который
   на 8 ГБ тоже приходится стримить. DWD-голова pi-H3 предсказывает пиксели прямо из признаков последнего
   шага: ~1.2 ГБ весов и оконное внимание.
3. **Pruned AdaLN.** Проекции AdaLN в исходной модели — 13B из 33B параметров. В pruned-версии они
   свёрнуты до ранга 8 (точность 1.5e-5), поэтому блок — это чистые 385M параметров attention+FFN.
4. **LoRA вливается при конвертации.** Во время генерации нет ни LoRA-весов, ни LoRA-матмулов:
   `W' = W + scale·B·A` считается в fp32 один раз, затем вращение и квантование.
5. **Text refiner и context_embedder переезжают в текстовую стадию.** Они не зависят от шага
   диффузии, поэтому считаются один раз на промпт и кэшируются вместе с эмбеддингами.
   В FreeVideo/diffusers refiner пересчитывается на каждом шаге.

## 2. Формат весов: свой «упакованный блок»

Конвертер (`tinyh3 convert`) один раз переводит HF safetensors в хранилище TinyH3:

```
models/<имя>/
  manifest.json            архитектура, рецепт, политика квантования, оффсеты всех тензоров
  dit/globals.safetensors  proj_in/out, audio proj, norm_out, таблица времени, DWD norm
  dit/block_000.bin …      50 файлов: каждый блок — ОДИН непрерывный буфер, выровненный по 4 КиБ
  dwd/head.safetensors     голова DWD (bf16)
  text/embed.bin           таблица эмбеддингов [151936, 5120] bf16 — читаем только нужные строки
  text/layer_000.bin …     50 слоёв Qwen3 (int8, поканально)
  text/refiner.bin         context_embedder + 2 блока refiner
  audio_vae/, tokenizer/
```

Почему один буфер на блок: при стриминге блок едет одной операцией `read` (диск → pinned ОЗУ)
и одним `cudaMemcpyAsync` (ОЗУ → VRAM). Тензоры внутри — это просто view на слот видеопамяти.
FreeVideo перекладывает safetensors потензорно, а это десятки маленьких копий и разбор заголовков
на каждом шаге.

### Квантование (ConvRot + int8/int4)

- Вход каждого линейного слоя вращается блочной матрицей Адамара H256 (та же, что в ComfyUI
  `*_int8_convrot` и в pruned-модели), веса вращаются так же при конвертации:
  `(x·H)(W·H)ᵀ = x·Wᵀ`. Вращение размазывает выбросы активаций, и после него int8 почти не теряет точности.
- **W8A8**: int8 веса с масштабом на выходной канал, int8 активации с масштабом на строку.
- **W4A8**: int4 веса группами по 128 по оси K (масштаб fp16 на группу), int8 активации.
  В ядре int4 распаковывается в int8 и считается на **int8 тензорных ядрах**.
- Q, K и V сливаются в одну матрицу `[21504, 5376]`: один GEMM вместо трёх и одно квантование входа.

Почему int8-вычисления, а не bf16: у GeForce Ampere (3070) пиковые fp16/bf16 с fp32-накоплением
равны 40.6 TFLOPS, а int8 — 162.6 TOPS. Получается в 4 раза быстрее на линейных слоях.

Политики (размер DiT на диске и в памяти):

| Политика | Блок | 50 блоков | Для кого |
|---|---|---|---|
| `int8` | 387.6 МБ | 19.4 ГБ | ≥ 24 ГБ ОЗУ, максимум качества |
| `mixed` (по умолчанию) | int8 для блоков 0–2 и 47–49, остальные int4 | 11.2 ГБ | 16 ГБ ОЗУ |
| `int4` | 200.7 МБ | 10.0 ГБ | 16 ГБ ОЗУ, максимум скорости |

## 3. Память: три яруса и планировщик

Каждый блок живёт в одном из ярусов: **VRAM-резидент**, **pinned-ОЗУ** или **диск**.
Планировщик (`tinyh3/planner.py`, `tinyh3 plan`) решает это перед каждым запуском по реальным
`mem_get_info`, доступной ОЗУ (с учётом cgroup) и геометрии запроса.

Бюджет VRAM для 3070 (8 ГБ; ~7.3 ГБ свободно на Windows с рабочим столом):

```
  CUDA-контекст и библиотеки          ~0.45 ГБ (замеряется)
  резерв от фрагментации               0.35 ГБ
  глобальные веса DiT                 ~0.05 ГБ
  активации (зависят от числа токенов) 1.0–2.0 ГБ (см. ниже)
  слоты стриминга: 2 × размер блока    0.4–0.8 ГБ
  остаток → VRAM-резидентные блоки     ~3.5–4.5 ГБ → 17–22 int4-блока
```

Активации ограничены жёстко: внимание идёт **группами голов**. QKV считаются только для группы
из `g` голов, внимание тоже по группе, а выходная проекция накапливается частичными суммами по оси K.
FFN режется на куски по токенам. Пик примерно `L·D·(2 + 3g·128/D)` байт при `L` токенах
вместо `L·(3·7168 + 28672)·2`.

Пример: 512×896, 5.2 с (124 кадра) → 37 латентных кадров × 448 токенов + ~400 аудио + ~300 текста
≈ **17.3 тыс. токенов**. Активации ~1.3 ГБ при группе в 8 голов.

### Расписание стриминга

- Порядок блоков фиксирован и повторяется на каждом шаге, поэтому расписание циклическое:
  предзагрузка блоков шага `s+1` начинается ещё на хвосте шага `s`.
- Отдельный CUDA-поток копирования, кольцо из 2–3 слотов в VRAM, синхронизация через события.
  Вычисления ждут только своё событие.
- Нерезидентные блоки **перемешаны** с резидентными (распределение Брезенхэма), а не идут хвостом:
  каждая копия перекрывается вычислением соседних резидентных блоков.
- Ярус «диск»: фоновый поток читает блоки в кольцо pinned-буферов в порядке вычислений.

Почему стриминг не тормозит: при 17 тыс. токенов один блок считается ~0.3–0.5 с на 3070,
а int4-блок (200 МБ) едет по PCIe 4.0 x16 за ~10 мс. Расчёт упирается в GPU, а не в шину.
Даже 28 нерезидентных блоков — это ~0.3 с трафика на шаг против ~20 с вычислений.

## 4. Текстовая стадия (отдельный процесс)

Qwen3-VL-32B (50 слоёв) — 24.4B параметров, это больше самого DiT. Решение:

- Свой потоковый декодер Qwen3 только для текста: слои int8, грузятся по одному
  с упреждающим чтением в фоне. Расчёт на ~300 токенах тривиален, всё упирается в чтение диска
  (~24 ГБ: NVMe ~8–12 с, SATA ~45 с).
- Из таблицы эмбеддингов (1.56 ГБ) читаются только строки нужных токенов.
- Сразу после 50-го слоя на том же GPU считаются `context_embedder` и 2 блока refiner.
- Результат `[T, 5376]` кэшируется на диске по хэшу промпта: повторный промпт пропускает стадию целиком.
- Процесс завершается и отдаёт системе всю ОЗУ и VRAM до старта DiT.

## 5. Стадия денойзинга

Шаг `i` из 2/4:
1. `temb` из pruned-таблицы времени → модуляции AdaLN для всех 50 блоков (крошечные таблицы).
2. Для каждого блока: `RMSNorm → modulate → H256-вращение → int8` одним проходом,
   затем QKV-GEMM по группе голов → QK-RMSNorm + RoPE → внимание (SageAttention2, иначе
   FlashAttention через SDPA) → частичная out-проекция. Потом FFN кусками: GEMM → SwiGLU →
   вращение и квантование → GEMM → residual с gate.
3. Шаг Эйлера отдельно для видео- и аудиорядов (pi-Flow: shift 12 для видео, 3 для аудио).
4. На последнем шаге сохраняются признаки DWD (`dwd_norm_out`) — пиксели берутся из них.

## 6. Стадия DWD и звук

- Блоки DiT выгружаются, загружается голова DWD (1.2 ГБ).
- 8 слоёв Sol: оконное внимание 5×16×16 со сдвигом и глобальные токены на каждый 5-латентный блок.
  Окна идут пачками, FFN — кусками, поэтому пик памяти ограничен.
- Аудио-VAE декодирует стерео 32 кГц. Затем mux в MP4 (H.264 + AAC) с метаданными генерации.

## 7. Процессы, сервер, интерфейс

- `tinyh3 serve` поднимает FastAPI-сервер: очередь задач (SQLite), прогресс по WebSocket, галерея.
- Каждая стадия запускается в своём дочернем процессе (`spawn`). Так гарантируется освобождение
  памяти между стадиями, и падение по OOM не роняет сервер.
- При OOM задача перезапускается с более лёгким планом: меньше резидентных блоков → меньше
  группа голов → меньше кусок FFN.
- Интерфейс — одна страница без сборки (HTML/CSS/JS): промпт, пресеты качества,
  разрешение и длительность с оценкой времени и памяти до запуска, живой прогресс по стадиям, галерея.

## 8. Фоллбэки

| Возможность | Быстрый путь | Фоллбэк |
|---|---|---|
| W8A8 / W4A8 GEMM | Triton int8 tensor cores | `torch._int_mm` (W8A8) / деквант в bf16 + matmul |
| Вращение+квант, modulate | Triton fused | эталон на PyTorch |
| Внимание | SageAttention2 | `F.scaled_dot_product_attention` (Flash) |
| Чтение с диска | поток упреждения в pinned-кольцо | синхронное чтение |

Эталонная реализация на PyTorch (`tinyh3/kernels/reference.py`) — источник истины для тестов
и путь для CPU. Тесты сверяют наш DiT, текстовый энкодер и Sol-голову с diffusers/transformers
на маленьких случайных конфигурациях.
